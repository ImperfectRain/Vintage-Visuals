Vintage Visuals — Autonomous Renderer Architecture & Implementation Plan
Repository: ImperfectRain/Vintage-Visuals
Target: Vintage Story 1.22.7
Current recovery line: zero-sampler terrain baseline after terrain PBR fail-closed recovery
Primary objective: evolve Vintage Visuals from a collection of shader patches into a robust, modular rendering platform that is fast, safe, easy to extend, and suitable as a near-default visual upgrade for most Vintage Story users.
0. Operating mandate
You are the implementation agent for Vintage Visuals.
Work autonomously. Do not pause for user clarification when an answer can be obtained from:
the current repository and git history;
Vintage Story 1.22.7 shader/API source available locally;
runtime shader dumps/logs generated by the mod or game;
official OpenGL/Khronos documentation;
maintained Vintage Story shader-mod code and documentation;
reputable rendering-engine references.
If evidence is ambiguous, research it. If the answer is still ambiguous, choose the safest reversible implementation, document the uncertainty, and continue. Prefer small checkpoint commits over speculative rewrites.
Never claim runtime rendering, visual quality, stability, or performance has been verified unless the game was actually run and observed.
The system must fail closed. A cosmetic feature may turn itself off. Terrain rendering may never disappear because one optional resource failed.
1. Product north star
Vintage Visuals should become the visual overhaul that is easy to recommend to almost any Vintage Story player.
The target experience is:
install
→ mod inspects current game / renderer / GPU capabilities
→ builds the safest highest-quality compatible render profile
→ compiles/caches only required shader variants
→ enables strong defaults
→ degrades individual unsupported features rather than disabling the renderer
→ exposes simple Recommended / Performance / High / Ultra controls
→ remains debuggable through a Render Health report
The project must optimize for:
visual value per millisecond;
stable vanilla integration;
predictable fail-closed behavior;
low CPU and GPU overhead while idle;
easy addition of new features;
minimal duplication of shader logic;
strong compatibility across GPUs/drivers;
clear diagnostics instead of silent failure;
runtime quality scalability;
preservation of Vintage Story's visual identity.
The product should not become a generic photorealistic shader pack. The visual promise is:
Vintage Story as remembered, but with materials, weather, atmosphere and light behaving as if the renderer had been rebuilt years later.
2. Current known state and lessons
2.1 Recovery state
Recent recovery work established several important facts.
The catastrophic terrain corruption was removed by fail-closing the terrain PBR patch groups. The recovery gate prevented the main pseudopbr and pseudopbrtopsoil groups from modifying chunkopaque and chunktopsoil, restoring vanilla terrain rendering.
A zero-sampler identity patch was then added as the first staged restoration checkpoint. A follow-up commit restored the lightPosition declaration because the patch engine's token operation replaces its matched source rather than automatically reinserting it.
This is not a minor implementation detail. It is an architectural lesson:
A patch must be reasoned about as a source transformation, including what original source is removed by the transformation.
The system must stop relying on every GLSL snippet author remembering to paste an anchor declaration back manually.
2.2 Recovery fixes that should remain
Preserve the following concepts unless runtime evidence proves otherwise:
vanilla outGlow.g behavior on terrain/topsoil;
no production canopy-godray injection through the old vvCanopyShaft -> outGlow.g design;
safe normalization helpers for potentially zero-length vectors;
neutral canopy-context fallback while the canopy resource is not safely bound;
fail-closed optional resource behavior;
staged terrain restoration rather than wholesale re-enabling;
explicit runtime/static validation around terrain shader changes.
2.3 Important failure classes discovered
The project has encountered or narrowly avoided:
replacement patches deleting load-bearing vanilla declarations;
sampler declaration / binding surface changes breaking vanilla terrain;
potential texture-unit collisions or unsafe state assumptions;
native UI composer lifecycle crashes;
recursive scene-reflection feedback;
depth precision failure in screen-space reflections;
debug views capturing their own debug output;
foliage transmission sign errors;
foliage classification being used with stronger semantics than originally validated;
expensive canopy inference performed per fragment;
visually impressive architecture that had not yet been runtime validated.
These failures should drive permanent engineering safeguards.
3. External architectural lessons to incorporate
Use outside references as design input, not as unquestioned templates.
3.1 ShaderPatchesLib / Coriaender-style patch safety
Relevant ecosystem patterns include:
preserving matched source explicitly when augmenting it;
transactional patch groups;
explicit target program lists;
shader reapplication on every shader load/reload;
build-time GLSL validation;
visible failure reporting;
separating expensive effects into dedicated passes when practical.
Vintage Visuals should adopt the principles without adding a dependency unless doing so is clearly advantageous.
3.2 Compiler-style render architecture
Modern renderer design increasingly uses compiler/graph thinking:
describe feature/resource requirements declaratively;
resolve dependencies;
specialize shader variants;
validate generated output;
schedule or omit work based on capabilities;
cache expensive compilation products.
Vintage Visuals does not control Vintage Story's entire renderer, so it does not need a full Vulkan-style render graph. It should nevertheless adopt a small compiler + capability graph + resource graph.
3.3 OpenGL resource lessons
The renderer must treat linked-program state as authoritative. Do not assume:
sampler declaration order equals safe binding;
a hardcoded texture unit remains unused across game updates;
a uniform exists because source contains its declaration;
a previous shader reload preserves current uniform locations;
active texture state is harmless after custom binds.
Use runtime introspection wherever available.

5. Phase 1 — Make the patch engine safe by construction
This is the highest-priority architectural refactor after the current zero-sampler runtime checkpoint is proven.
5.1 Add typed patch operations
Replace the current implicit "token means replacement" mental model with explicit operations:
ASSERT
Prove source exists. Do not modify it.
type: assert
tokens: "uniform vec3 lightPosition;"
INSERT_BEFORE
Preserve the matched source and insert content before it.
INSERT_AFTER
Preserve the matched source and insert content after it.
REPLACE
Explicitly replace the matched source. Use only when intentional.
WRAP
Replace source while making the exact original text available to the replacement.
Conceptual syntax:
type: wrap
tokens: "outColor = ..."
content: |
  ${MATCH}
  outColor = vvApplyPbr(...);
REPLACE should be the dangerous operation, not the default operation.
5.2 Preserve exact match text automatically
Implement a ${MATCH}-style substitution or equivalent.
The patch engine, not individual GLSL snippets, should own source preservation.
After this change, snippets such as pbrcore.glsl should not need to reproduce the matched uniform vec3 lightPosition; simply because of patch mechanics.
Migrate existing patches incrementally and verify generated source before removing old defensive reinsertion.
5.3 Transactional groups remain mandatory
A patch group must obey:
all required anchors valid
→ produce complete transformed program

one required anchor invalid
→ no partial application
However, split broad groups into capability-sized groups where independent fallback is safe.
Recommended conceptual groups:
terrain-base
terrain-material-primary
terrain-material-secondary
terrain-weather
terrain-flora
terrain-scene-reflection
terrain-world-reflection
terrain-debug
Do not mechanically split until dependencies are understood. A group should be the smallest unit that can fail independently without invalidating the program.
5.4 Add source-contract tests
For every patch operation, test:
anchor matched exactly as expected;
number of matches;
declarations present before and after;
required vanilla statements preserved;
no unexpected duplicate declaration;
no accidental deletion of vanilla sampler/uniform/varying;
output assignment still present;
vertex/fragment varying contracts still agree.
Tests should compare before vs after, not only search for desired strings.
5.5 Generate a patch manifest
For every patched shader program produce a development artifact containing:
program
base source hash
applied groups
patch operations
matched anchors
preserved declarations
added declarations
samplers before
samplers after
varyings before
varyings after
final source hash
validation result
This should be written to a stable diagnostics directory whenever development tracing is enabled.
6. Phase 2 — Runtime shader/program introspection
The project must stop treating source layout as sufficient proof of runtime correctness.
6.1 Program introspection
After shader link, record where supported:
active uniform list;
active sampler uniforms;
assigned sampler units;
uniform locations;
relevant block bindings;
program ID;
link status;
validation status;
target program name.
For terrain programs, log the complete sampler map.
6.2 Texture unit allocator
Replace long-term hardcoded unit ownership with a program-aware allocation system.
Conceptual API:
TextureBindingPlan BuildBindingPlan(
    ShaderProgram program,
    IReadOnlyList<ResourceRequirement> vvResources);
The allocator should:
inspect active vanilla samplers;
determine units already occupied;
query relevant hardware limits;
allocate compatible VV resources;
explicitly assign sampler uniforms;
validate there are no collisions;
return an immutable binding plan.
Do this per linked program, because chunkopaque, chunktopsoil, entities, and future water shaders may expose different sampler surfaces.
Do not assume unit 7 or unit 15 is universally free.
6.3 Explicit binding state contract
Read the actual Vintage Story BindTexture2D implementation and determine:
whether it leaves a different active texture unit;
whether callers rely on active-unit state afterward;
whether binding has other side effects;
whether state is restored by the engine.
The VV binding layer must preserve whatever contract the surrounding renderer expects.
If necessary:
capture relevant prior state
bind VV resources
restore expected state
Do not perform unnecessary global GL state queries per draw if a cheaper deterministic contract is available.

8. Phase 4 — Reduce sampler pressure
8.1 Investigate a material texture array
The two material atlases are unusually well suited to a texture array because they share:
dimensions;
layout;
UV mapping;
update cadence;
ownership.
Investigate replacing:
sampler2D vv_materialTex;
sampler2D vv_materialTex2;
with:
sampler2DArray vv_materialData;
Suggested layers:
layer 0: normal X, normal Y, roughness, specular
layer 1: metalness, height, AO, emission
Benefits:
two samplers become one;
identical UV alignment by construction;
future material extension can add a layer without adding a sampler;
simpler resource ownership.
Do not migrate blindly. Validate:
Vintage Story/OpenGL target support;
upload path;
filtering semantics;
atlas page handling;
memory;
texture-size limits;
material debug views.
If the texture-array path is less stable on supported hardware than the current textures, keep the current architecture.
8.2 Structural shader variants
Major optional resources should disappear from the linked program when disabled.
Generate compile-time feature defines such as:
#define VV_FEATURE_MATERIAL_SECONDARY 1
#define VV_FEATURE_SCENE_REFLECTION 0
#define VV_FEATURE_WORLD_REFLECTION 1
Then declarations and code are guarded by compile-time branches.
Do not carry inactive samplers simply because a shared snippet contains them.
Runtime uniforms remain appropriate for lightweight aesthetic values and values expected to change frequently.

15. Reflection architecture
Preserve the current hybrid intent:
SSR scene history
→ world-space geometry/radiance approximation
→ analytic environment fallback
Do not let reflection failure disable materials.
15.1 Long-term improvement
If per-fragment world DDA is too expensive, investigate a dedicated lower-resolution reflection evaluation pass.
Potential benefits:
fewer DDA traversals;
easier temporal stabilization;
less duplicated work;
fewer terrain-fragment instructions.
Do not implement until GPU timing confirms it is worthwhile.
15.2 Feedback
Scene capture currently uses a previous finished frame and therefore can contain reflections.
The current luma/hue heuristic is a mitigation, not a principled recursion solution.
Long-term options to research:
capture before reflective composition if a safe stage exists;
separate reflection source buffer;
confidence reduction using authoritative world geometry;
temporally stable non-recursive radiance source.
Do not prioritize this over terrain stability/performance.

27. Decision rules
Use these rules when choosing among implementations.
Correctness
Prefer the implementation that preserves vanilla renderer contracts.
Failure behavior
Prefer a feature that disappears cleanly over one that can corrupt shared terrain state.
Performance
Prefer moving work to a cheaper update cadence over optimizing expensive per-fragment work.
Resources
Prefer sharing/packing resources when semantics and lifecycle align.
Complexity
Do not build general-purpose infrastructure unless at least two real systems need it or a known failure class demands it.
Compatibility
Do not require modern optional GL extensions for the default path.
Visual quality
Prefer systems that produce clear screenshot/gameplay improvement rather than technically impressive but subtle behavior.

33. Definition of success
This restructuring succeeds when all of the following are true:
ordinary terrain shader patching cannot accidentally delete a matched declaration without using an explicit replacement operation;
optional shader features are resolved through capabilities rather than one global kill switch;
texture bindings are program-aware and validated;
GPU resources have one clear owner and lifecycle;
disabled features are absent from shader variants where practical;
a missing reflection/canopy/material resource cannot break terrain;
generated shaders are statically compiler-validated;
runtime health diagnostics explain what is active and why;
the project can add new systems without expanding one monolithic pseudopbr.glsl indefinitely;
quality tiers reduce actual work, not only effect strength;
runtime tests confirm terrain, topsoil, fog, water interaction and vegetation remain stable;
the default profile provides a high visual payoff at a reasonable cost;
users can install the mod without understanding its renderer internals.
